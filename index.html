Superpowers: методология как исполняемый артефакт

Плагин, который превращает кодинг-агента в дисциплинированного инженера. Ядро — четырнадцать markdown-скиллов; вся архитектура подчинена двум ресурсам: контекстному окну и доверию к процессу.

01 · система целиком

HLD: пять слоёв, данные в ядре

Ядро проекта — чистые данные: markdown-файлы со скиллами. Исполняемая логика вытеснена на периферию — один bash-хук активации и тонкие адаптеры под каждую платформу. Поэтому одна и та же библиотека работает в одиннадцати харнессах, а изменения ядра не требуют пересборки чего-либо.

02 · механизм активации

Bootstrap: как скиллы попадают в голову агента

LLM не пойдёт искать скиллы сам. Поэтому на каждом старте сессии хук принудительно вливает в контекст полный текст using-superpowers — полиси с правилом «если есть хоть 1% шанс, что скилл применим, ты обязан его вызвать». Ключевая деталь — matcher включает compact: сжатие контекста стирает полиси, и хук инъецирует её заново.

03 · процесс

Сага: от идеи до merge, пять гейтов человека

Скиллы сцеплены в долгоживущий процесс: терминальное состояние одного — вход следующего. Brainstorming может вызвать только writing-plans — перепрыгнуть фазу нельзя. Человек появляется ровно в пяти точках; между ними агент работает автономно, и «Should I continue?» прямо запрещён.

04 · исполнение

SDD: файловая шина вместо разговоров

Всё, что попадает в промпт диспетча или ответ сабагента, остаётся в контексте контроллера до конца сессии и перечитывается на каждом ходу. Поэтому крупные артефакты — бриф, отчёт, ревью-пакет — текут через диск, а контроллер видит только пути и статусы длиной до пятнадцати строк. Ledger — append-only журнал — единственная память, переживающая compaction.

05 · отказоустойчивость

Fix loop: пять раундов и предохранитель

Ревью с findings запускает цикл: раунд = один fix-диспетч плюс одно скоупленное ре-ревью. Ре-ревьюер выносит вердикт только по списку findings и поломкам в fix-диффе — «гулять» по коду ему нельзя, иначе цикл не сойдётся никогда. Застрявший цикл — сигнал, что имплементер не видит собственную проблему: с четвёртого раунда его меняют на свежего с моделью на тир выше.

06 · доменная карта

DDD: контексты и их отношения

Домен проекта — не код, а управление поведением агента. Ядро говорит на published language (markdown + frontmatter), который обязаны понимать все потребители; адаптеры подчиняются API своих платформ; evals стоят к ядру в отношении customer–supplier — изменение скилла без before/after-доказательств не принимается.

07 · размещение и данные

Deployment: система живёт в трёх местах

Ни одна из предыдущих схем не отвечала на практический вопрос «что где физически лежит». Ответ: система существует в трёх копиях — исходник на GitHub, установленная копия внутри харнесса и артефакты, которые агент порождает в проекте пользователя. У каждого места свой владелец и свой цикл обновления.

Data lifecycle: что переживает что

У каждого артефакта процесса — своя продолжительность жизни. Ключевой механизм: после чистого финального ревью workspace уничтожается (rm -rf), и единственной записью о работе остаётся git history — «the git history is the record now».

08 · опциональный контур

Visual Companion: единственный сервер в проекте

Слепая зона большинства описаний Superpowers: рядом с «ядром из чистого markdown» живёт полноценный веб-сервер — 723-строчный server.cjs для показа мокапов в браузере во время brainstorming. Жемчужина №1 — полиглот run-hook.cmd. Один файл — одновременно валидный cmd-батник и bash-скрипт: для bash всё тело батника — heredoc-комментарий, для cmd.exe строка : << 'CMDBLOCK' — мусор, который он молча пропускает. Windows ищет Git-bash по стандартным путям и тихо выходит, если его нет — плагин деградирует без ошибки, теряя только инъекцию.

Жемчужина №2 — task-brief: 15-строчный awk-парсер вырезает задачу N из плана по заголовку Task N, отслеживая code-fences, чтобы «Task» внутри примеров кода не считался заголовком. Именно этот скрипт делает возможной файловую шину рис. 4 — текст задачи не проходит через контекст контроллера.

10 · python-инструмент

Token analyzer: чиним прибор, который меряет экономику

Единственный Python-файл в проекте — tests/claude-code/analyze-token-usage.py. По статусу «утилита для тестов», по сути — единственный инструмент, численно проверяющий тезисы секций 07 и wiki 06–07: парсит JSONL-транскрипт сессии и раскладывает токены на контроллер и сабагентов.

Что было не так: оригинал считал cache-токены по цене обычного input ($3/M). Реальный прайсинг: cache read = 0.1× базовой ставки, cache write = 1.25×. Сессии Claude Code на 90%+ состоят из cache reads — старая формула завышала стоимость на порядок. Прибор, созданный измерять экономику контекста, искажал главную статью расходов этой самой экономики.

Добавлено: метрики методологии (cache hit rate, cost-per-turn, доля контроллер/сабагенты — численное доказательство файловой шины), детектор dispatch-bloat (промпт диспетча >20k символов — тот самый анти-паттерн «42k символов пасты» из SDD-скилла), взрослый CLI (--json, --html, --by-model, --top N), честный подсчёт битых строк на stderr вместо молчаливого except: pass, и golden-тест на 14 assertions в конвенции проекта.

Совместимость: скрипт уже дёргается из test-subagent-driven-development-integration.sh под set -euo pipefail. Новая версия — drop-in замена: тот же вызов, тот же exit 0 на успехе.

12 · выводы

Что унести с собой

  1. Промпты — это софт. Версии, CI через evals, запрет правок без тестов, история создания. Формулировки скиллов — оттюненные веса, их не правят по вкусу.
  2. Контекст — самый дорогой ресурс, и им управляют архитектурно. Файловая шина, одноразовые сабагенты, append-only ledger, lazy loading скиллов — полная аналогия с process isolation в ОС.
  3. Compaction — отказ узла; recovery проектируют заранее. Ре-инъекция bootstrap плюс ledger — WAL-recovery для агента: «trust the ledger and git log over your own recollection».
  4. Против рационализаций работает их перечисление. Таблицы «мысль → опровержение», собранные из реальных сессий, перехватывают уклонение в момент генерации мысли.
  5. Turn count beats token price. Дешёвая модель, делающая втрое больше ходов, дороже средней. А инвестиция в качество плана конвертируется в дешёвую модель исполнения.
  6. Циклам нужны предохранители. Жёсткий кап, эскалация тира, скоупленное ре-ревью, запрет silent discard — иначе агентские циклы либо бесконечны, либо обрываются молча.

00TL;DR — весь проект в 10 предложениях

Superpowers — это методология разработки для AI-кодинг-агентов, упакованная в plugin. Ядро — 14 markdown-«скиллов», которые инъецируются в контекст агента и меняют его поведение: вместо «сразу писать код» агент проходит дисциплинированный процесс.

Процесс: brainstorming (Socratic-диалог → спек) → git worktree (изоляция) → writing-plans (задачи по 2–5 минут) → subagent-driven development (свежий сабагент на задачу + двухступенчатое ревью) → финальное ревью всей ветки → merge/PR.

Механика активации: hook на старте сессии вливает скилл using-superpowers в контекст с правилом «если есть хоть 1% шанс, что скилл применим — ты ОБЯЗАН его вызвать». Это gateway ко всем остальным скиллам.

Ключевые инженерные решения: zero-dependency (ядро — чистые данные), файлы вместо текста в промптах (защита контекстного окна), ledger как event log (переживает compaction), явный выбор модели на каждую роль, circuit breaker на 5 fix-раундов.

Поддерживается 11 харнессов через тонкие адаптеры; сам core платформо-независим. Автор — Jesse Vincent (Prime Radiant). 94% PR-ов отклоняется: контент скиллов защищён eval-ами, менять его «по вкусу» запрещено.

01Что такое skill

Одна фраза: skill = исполняемое знание. Markdown-файл, который LLM «выполняет» как программу.

Анатомия

skills/<name>/
├── SKILL.md            ← точка входа (обязателен)
│   ├── frontmatter     ← name + description (триггер-условия!)
│   └── body            ← процесс, чеклисты, таблицы, dot-графы
├── *.md                ← справочные файлы, промпт-шаблоны
└── *.sh / *.js / *.ts  ← опциональные скрипты

Директория скилла — агрегат (в терминах DDD, см. 09): извне ссылаются только на корень superpowers:<name>, никогда на внутренние файлы.

Почему «код, а не проза»

Из CLAUDE.md: «Skills are not prose — they are code that shapes agent behavior». Следствия: изменение = поведенческий дифф и требует before/after eval-доказательств (12); формулировки — тюненые конструкции, а не стиль (10); рефакторинг «для соответствия документации Anthropic» прямо запрещён.

description = триггер

Frontmatter description — не документация, а условие срабатывания. Агент постоянно видит только name+description всех скиллов; полный текст загружается при вызове — lazy loading знаний (06).

02Активация: почему скиллы вообще срабатывают

Проблема: скиллы на диске — мёртвый груз, LLM не будет искать их сам. Решение: принудительная инъекция gateway-скилла в контекст на старте каждой сессии (механика — рис. 2 и СД-1).

Три детали, каждая важна:

  1. Matcher включает compact. Compaction стирает контекст — bootstrap инъецируется заново. Парный механизм восстановления — ledger (04).
  2. Один bash-скрипт эмитит три JSON-формата, ветвясь по env-переменным — анти-коррупционный слой в 50 строк. Claude Code читает оба поля без дедупликации, поэтому эмитить можно только одно.
  3. Не hook — так transform. OpenCode инъецирует через message transform (с кэшем контента), Pi — через extension. Порт другой, контракт тот же (08).

using-superpowers — не список скиллов, а полиси принуждения:

"If you think there is even a 1% chance a skill might apply… you ABSOLUTELY MUST invoke the skill."

Плюс таблица Red Flags — 12 «мыслей-рационализаций» с опровержениями (10), приоритет process-скиллов и субординация: инструкции человека > скиллы > дефолтное поведение.

Acceptance test интеграции: в чистой сессии сообщение «Let's make a react todo list» должно авто-триггернуть brainstorming до кода. Не триггерит — не интеграция.

03Workflow: сага от идеи до merge

Семь скиллов сцеплены в один долгоживущий процесс — терминальное состояние одного = вход другого (визуально — рис. 3 и СД-2).

Ключевые свойства

  • Гейты человека — ровно 5: одобрение дизайна, одобрение спека, рулинги «finding vs план», BLOCKED-эскалации, судьба ветки. Между ними — автономия; «Should I continue?» запрещён.
  • Анти-паттерн «слишком просто для дизайна» заблокирован явно: даже todo-list и config change проходят через дизайн. Дизайн может быть в 3 предложения — но обязан быть показан и одобрен.
  • Терминальные состояния жёсткие: brainstorming может вызвать только writing-plans — защита от перепрыгивания фаз.
  • Развилка исполнения: SDD (та же сессия, свежие сабагенты) vs executing-plans (параллельная сессия, батчи, человек в цикле).
  • События-переходы (DDD-сага): DesignApproved → SpecApproved → WorkspaceReady → PlanWritten → TaskCompleted×N → BranchReviewed → Merged. Компенсации: fix loop (05), BLOCKED.
04SDD: цикл одной задачи

Формула: fresh subagent per task + task review (spec + quality) + broad final review = high quality, fast iteration (визуально — рис. 4 и СД-3).

Роли

  • Controller — координатор; никогда не пишет код сам («controller fixes pollute your context and skip review»).
  • Implementer — свежий сабагент, одна задача; вопросы до начала работы поощряются.
  • Task Reviewer — двухступенчатая проверка: spec compliance, затем code quality.

Контракт статусов

статусреакция контроллера
DONEreview package → диспетч ревьюера
DONE_WITH_CONCERNSпрочитать concerns; про корректность/скоуп — решить до ревью
NEEDS_CONTEXTдать контекст, re-dispatch
BLOCKEDконтекст? → дать. Сложно? → модель выше. Велика? → разбить. План неверен? → человек

Ledger — память, переживающая compaction

.superpowers/sdd/<plan>/progress.md, append-only, идентичность в первой строке. Строка Task N: complete = не передиспетчеризовать: контроллеры, потерявшие место после compaction, передиспетчеризовали целые последовательности готовых задач — «the single most expensive failure observed». «Trust the ledger and git log over your own recollection».

Тонкости

  • BASE, не HEAD~1 — иначе молча теряются все коммиты многокоммитной задачи, кроме последнего.
  • Никакого пре-джаджинга ревью — «не флагай X» запрещено; спорное разруливается адъюдикацией.
  • Дисптач описывает одну задачу — реальный анти-кейс: 42k символов, 99% — вставленная история сессии.
  • Конфликты плана — батчем до Task 1, одним вопросом человеку.
05Fix loop: 5 раундов, эскалация, breaker

Триггер: Spec ❌, любой Critical/Important finding, или подтверждённый ⚠️ (визуально — рис. 5 и СД-4).

Два выхода до входа в цикл: Minor → сразу в ledger как deferred («a roll-up nobody reads is a silent discard»); finding против текста плана → решает человек.

Раунд = один fix-диспетч + одно scoped re-review. Максимум 5. R1–3 — resume оригинального имплементера (контекст цел). R4–5 — свежий имплементер, модель на тир выше: цикл, переживший три резюма, означает, что имплементер не видит свою проблему.

Гейт перед re-review: fix report обязан содержать покрывающие тесты + команду + вывод — отчёт и есть test evidence. Re-review скоуплен: только вердикты по списку findings + поломки в fix-диффе; out-of-scope → ledger, цикл не продлевают.

Breaker (R=5)

вердиктдействие
ревьюер неправ / спорноpark + ruling в ledger; финальное ревью увидит обе стороны
реально, ничего сверху не строитсяpark + ruling «real, deferred»
реально И load-bearingSTOP: BLOCKED, полный отчёт человеку

Адъюдикация только на капе (раньше = pre-judging); каждое решение — запись в ledger; silent discard запрещён.

06Экономика контекста

Контекстное окно — не буфер, а дорогая арендуемая память: всё, что попало в контекст контроллера, перечитывается на каждом ходу до конца сессии.

Приёмы

  1. Файлы как шина данных. Brief, report, review package передаются путями — данные текут через диск, минуя контекст контроллера (рис. 4).
  2. Свежий сабагент на задачу — не для параллелизма, а для гигиены: контроллер конструирует ровно нужный контекст.
  3. Ledger против compaction — истина живёт в append-only файле + git log.
  4. Lazy loading скиллов — постоянно в контексте только name+description.
  5. Короткие контракты возврата — имплементер возвращает ≤15 строк; детали в report-файле.
  6. Нарратив под запретом — «narrate at most one short line between tool calls».

Инвариант: контроллер = координатор с чистым контекстом; работа, требующая большого контекста, выносится в одноразовый сабагент. Полная аналогия с process isolation в ОС.

07Экономика моделей

Принцип: наименее мощная модель, которая справится с ролью. Анти-дефолт: «an omitted model inherits your session's model — often the most expensive» — поэтому модель указывается явно в каждом диспетче.

08Харнесс-адаптеры: 11 платформ, один core

Ports & Adapters в чистом виде: core — платформо-независимые данные, специфика — в тонких адаптерах (рис. 1).

Три стратегии активации под один контракт

  1. hook + JSON (Claude, Cursor, Copilot) — ветвление в одном bash-скрипте;
  2. message transform (OpenCode) — JS-плагин с кэшем bootstrap-контента;
  3. extension (Pi) — TS; у Pi нативные скиллы, Skill tool не нужен.

Словарь инструментов: OpenCode-адаптер несёт tool mapping (ACL на уровне языка): скиллы написаны в словаре Claude Code, адаптер переводит (Subagent → task, Read files → read…).

Манифесты — дубли метаданных в формате каждой платформы; единая версия 6.2.0 транслируется bump-version.sh.

Критерий настоящей интеграции: «If you are not sure whether your integration loads the bootstrap at session start, it does not». Отклоняются: копирование скиллов руками, npx-шимы, opt-in per session.

09DDD-карта проекта

Домен — не «код», а методология разработки для AI-агентов (визуально — рис. 6).

Поддомены

CORE ──────── Skills Library + Workflow-методология (skills/)
SUPPORTING ── Активация/Bootstrap · Мета-скиллы · QA/Evals
GENERIC ───── Харнесс-интеграция · Дистрибуция

Bounded contexts

Skill Authoring (скилл как исходник) · Skill Runtime (скилл как инструкция; здесь Plan, Ledger, роли) · Activation (ACL из трёх JSON-форматов) · Distribution. Одно слово «Skill» — разная семантика в первых двух = классический признак границы.

Отношения контекстов

  • Skills → харнессы: published language — Markdown + YAML frontmatter;
  • адаптеры → харнессы: conformist + ACL-словарь у OpenCode;
  • evals → skills: customer–supplier — правки только с eval-доказательствами.

Агрегаты и события

Skill — агрегатный корень (граница = директория, идентичность = frontmatter name). Workflow — сага с компенсациями. Ledger — event store процесса. Red Flags — policy-объекты (10).

Оценка: образцовый Ports & Adapters с ядром из чистых данных; zero-dependency — доменный инвариант. Слабое место — один bash-скрипт со знанием трёх протоколов инъекции.

10Behavior shaping: психология для LLM

Самая оригинальная часть проекта: скиллы закрывают известные пути уклонения LLM от процесса — документированные баги агентского поведения и патчи к ним.

  1. Red Flags / rationalization tables — «мысль-соблазн → опровержение», 12 строк в using-superpowers, своя таблица в SDD. LLM генерирует рационализацию → она уже в таблице → рядом опровержение. Прививка до болезни, собранная из реальных сессий.
  2. Усиление сигнала — <EXTREMELY-IMPORTANT>, CAPS, правило 1%: дешевле открыть скилл зря, чем пропустить нужный.
  3. Явные разрешения против выученной услужливости — «It is always OK to stop and say "this is too hard for me". Bad work is worse than no work» + формализованные статусы эскалации.
  4. Hard gates и терминальные состояния — «ни строчки кода до одобрения»; анти-паттерн «too simple» назван по имени.
  5. Запрет пре-джаджинга — маркеры перечислены буквально: «если в твоём промпте есть "do not flag" — стоп».
  6. Субординация — человек > скиллы > дефолт.

Гипотеза, почему работает: агент срезает углы, оптимизируя «казаться полезным сейчас»; таблицы перехватывают этот градиент в момент генерации мысли — few-shot negative examples, встроенные в полиси. Отсюда и 94% отклонённых PR: люди правят «странные» формулировки, не понимая, что странность — это и есть механизм.

12Тестирование и evals: как тестируют промпты

Контур 1 — инфраструктура (tests/): shell/mjs-тесты механики плагина. Деталь: триггеринг тестируется на haiku — проверка нижней границы: сработает на слабой модели — сработает на любой.

Контур 2 — поведение (superpowers-evals, внешний репо): харнесс drill гоняет реальные tmux-сессии Claude Code / Codex / Gemini CLI, скилл-комплаенс судит LLM-верифаер; PR требует adversarial pressure testing + before/after результаты.

Это зрелый ответ на «как CI-ить промпты»: функция стохастическая, спека — желаемое распределение поведения. Решение: (а) реальные сессии, не синтетика; (б) LLM-судья по рубрике; (в) сравнение до/после, не абсолютная оценка; (г) adversarial-давление. Отсюда запрет «compliance»-правок: формулировки — оттюненные веса.

Мета-скилл writing-skills замыкает цикл: система улучшает саму себя тем же процессом, которым улучшает чужой код.

13Инсайты: неочевидное, что стоит унести
  1. Промпты — это софт со всеми следствиями — версии, CI, запрет правок без тестов, история создания.
  2. Контекст — самый дорогой ресурс, и им управляют архитектурно, а не «пиши короче».
  3. Compaction — отказ узла; recovery проектируют заранее (bootstrap re-inject + ledger = WAL-recovery).
  4. Против рационализаций работает их перечисление — дешёвый переносимый приём для любых агентских полиси.
  5. Эскалация — штатный исход: без дешёвого способа сказать «не могу» агент будет врать.
  6. Turn count beats token price.
  7. Циклам нужны breakers — иначе бесконечность или молчаливый обрыв.
  8. Ядро из данных масштабируется почти бесплатно — markdown + интерпретатор на каждой платформе.
  9. Социальный слой — тоже архитектура: anti-slop-полиси формализована как инженерный артефакт.
  10. Открытые вопросы: bash-скрипт с тремя форматами — узкое место; Platform Adaptation — протечка адаптеров в core; жёсткость гейтов против трения пользователей — ручка, которую крутят выбором executing-plans vs SDD.
14Visual Companion: сервер внутри markdown-проекта

Опровержение собственного мифа: «zero-dependency ядро из чистых данных» соседствует с самым большим кодовым артефактом проекта — Node-сервером на 723 строки (skills/brainstorming/scripts/server.cjs) плюс клиент helper.js и 9 тест-файлов (~35% всего кода). Точная формула: ноль обязательного кода — companion строго опционален и запускается только с согласия человека.

Механика (рис. 9 атласа)

  • Транспорт — файловая система, как и в SDD: агент пишет screen-*.html в session-директорию, сервер ловит их через fs.watch и рассылает браузеру reload по WebSocket. Контент никогда не идёт от агента по сети.
  • Auth: токен → query key → cookie (имя куки привязано к порту), timing-safe сравнение. Порт и токен персистятся — рестарт сервера переиспользует их, и открытая вкладка переживает рестарт.
  • Устойчивость клиента: reconnect с экспоненциальным backoff 500ms→30s, «paused»-оверлей после 15 секунд разрыва.
  • Телеметрия — логотип с primeradiant.com с версией в URL: единственный внешний запрос всей системы. Opt-out: SUPERPOWERS_DISABLE_TELEMETRY, DISABLE_TELEMETRY, CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC.

Поведенческий слой

Скилл brainstorming жёстко регулирует использование: предлагать только just-in-time (первый реально визуальный вопрос, не раньше), отдельным сообщением, и решать per-question — «вопрос о UI-теме ≠ визуальный вопрос». Тот же приём поимённого запрета соблазнов, что и в 10.

15Token analyzer: чиним прибор, который меряет экономику

Единственный Python-файл проекта — tests/claude-code/analyze-token-usage.py. По статусу «утилита для тестов», по сути — единственный инструмент, численно проверяющий тезисы 06 и 07: парсит JSONL-транскрипт сессии и раскладывает токены на контроллер и сабагентов (визуально — рис. 10).

Что было не так

Оригинал считал cache-токены по цене обычного input ($3/M). Реальный прайсинг Anthropic: cache read = 0.1× базовой ставки, cache write = 1.25×. Сессии Claude Code на 90%+ состоят из cache reads — старая формула завышала стоимость на порядок. Прибор, созданный измерять экономику контекста, искажал главную статью расходов этой самой экономики. Второй баг: один прайс на все агенты, хотя message.model есть в каждой строке транскрипта — при том, что вся секция Model Selection в SDD-скилле посвящена выбору модели по роли.

Что исправлено

  • Прайсинг по классам токенов и по тирам моделей (opus/sonnet/haiku, читается из message.model); оверрайд — --price-input/--price-output или --pricing-file.
  • Метрики методологии: cache hit rate, cost-per-turn, доля контроллер/сабагенты (численное доказательство файловой шины из 04/06), детектор dispatch-bloat (промпт диспетча >20k символов — анти-паттерн «42k символов пасты» из SDD-скилла).
  • Взрослый CLI: --json, --html PATH, --by-model, --top N, --no-color (уважает NO_COLOR).
  • Честность вместо тишины: except Exception: pass заменён на подсчёт битых строк, репортится на stderr — stdout остаётся стабильным отчётом.
  • Рефакторинг: @dataclass Usage с __add__ убрал пятикратное дублирование; чистые функции прайсинга тестируются отдельно от парсинга.
  • Golden-тест на 14 assertions в конвенции test-sdd-workspace.sh. Ключевая проверка регрессии: сессия с 82k cache-read токенов должна стоить <$0.10 — вернётся плоский прайсинг, тест покраснеет.

Совместимость: скрипт уже дёргается из test-subagent-driven-development-integration.sh под set -euo pipefail. Новая версия — drop-in замена: тот же вызов, тот же exit 0 на успехе, проверено прогоном точно такого вызова плюс граничные случаи (пустой транскрипт, битые строки, отсутствующий файл).
